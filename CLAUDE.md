# Watt Dungeon: notes for Claude

- Vanilla JS ES modules, Vite, and three.js **pinned to r128** (0.128.0). The lighting and colours are tuned for r128's legacy lighting. Upgrade three.js only as its own deliberate change.
- Four pages. The ARPG (`index.html`, `src/`) is the main game. The map viewer (`maps/index.html`, `src/maps/`) is a dev tool that draws generated level layouts by seed; the game's `?seed=N` plays the same layouts (`G.devSeed`). The original pedal demo (`pedal/index.html`, `pedal/src/`) is kept as a reference and isn't being developed. The asset gallery (`gallery/index.html`, `src/gallery/`) browses every imported KayKit model and animation so the owner can pick what to use; its files are in `public/gallery/`, made by `scripts/prep-gallery.mjs`, and the game doesn't load them.
- ARPG shared mutable state lives in `src/core/state.js`: `G` (world), `P` (player) and `S` (derived stats, refreshed by `recalc()`). Mutate fields on those objects; don't export reassignable `let`s.
- ARPG game code reads input only via `ctl` (`src/input/input.js`). Devices (keyboard + mouse and touch today; Zwift Ride and KICKR later) live in `src/input/` and write into `ctl`. Never read DOM events or sensors from game code. RIDE mode (`src/input/ridesim.js`) simulates the Zwift Ride and KICKR and adds `ctl.auto` (autopilot) and `ctl.effort` (`{ pw, rel, cad }`); game code turns effort into movement, cast speed and Surge via `effortMods`. There is no mana: skills are limited by cast time and cooldowns, and the Surge gauge (`SURGE` in `src/data/skills.js`; Shift or ⚡ on keyboard and touch) is the only resource (tuning in `src/data/ride.js`).
- Every gameplay and balance number lives in `src/data/`, never in game code. Visual, physics and animation numbers (particles, knockback, steering) can stay in code. Where things go:
  - `skills.js` (`SK`, `SURGE`): each skill's cast time, cooldown, damage multiplier, radius, range and duration; burning ground; the flask.
  - `gems.js`: gems, slots, sockets, milestone numbers (`mile`), support gems and their numbers (`SUPPORTS`), gem drops, feeding.
  - `monsters.js`: monster stats, tiers, packs, rare affixes (`RARE`), status effects (`STATUS`), how monsters fight (`FIGHT`), death blasts (`BLAST`), the guardian (`BOSS`).
  - `items.js`: bases, affixes, uniques and their effect numbers (`EXTRA`), drop chances (`DROP`).
  - `balance.js`: hero growth, rarity multipliers, hit spread and death penalty (`COMBAT`), XP curve, item scaling, par levels, par gear and supports, targets.
  - `graphics.js`: look tuning, including the LOOK styles.
  - Support and milestone text shown to players sits next to its numbers; `npm test` fails if they drift apart.
- Balance maths lives in `src/game/formulas.js` (pure, imports only data) so the game and the tools share it. After changing balance numbers run `npm run balance` (instant maths report) and `npm run arena` (scripted fights with the real game, needs a build); `npm test` has balance guard rails. See "Balance" in `docs/design-notes.md`.
- The hero is a melee knight: the Main gem (the starting Sword; Ember Cleave, Frost Strike, Thunder Slam; one data-driven module, `src/game/sk/strike.js`) auto-attacks what's in reach (`ctl.autoAtk`, the ATTACK toggle), and the autopilot walks into swing reach. The skill is timing, not positioning: the Knight's Shield (Guard: hold to block, press to parry; `src/game/sk/guard.js`), Roll (Evade, `src/game/sk/roll.js`), Flex skills and Surge. Every big threat is answered by a button, never by where you stand; monster hits pass `{ from, kind, by }` to `hurtP` (`kind`: hit, heavy, unblockable). Stagger is in `src/game/combat.js`. Design: "Fight mechanics" in `docs/design-notes.md`.
- Not released yet: **no save compatibility.** When the save format or content changes, bump `KEY` in `src/game/save.js` and old saves are ignored; don't write migration code.
- Characters (the hero is `hero_knight.glb`; `scripts/prep-hero.mjs` rebuilds it from the gallery copy without the packs), extra clips (`anims_new.glb`, from Character Animations 1.1) and the dungeon pieces (`dungeon.glb`) are KayKit `.glb` files in `public/models/`, generated by `scripts/prep-models.mjs` from the KayKit packs (GitHub clones plus itch.io zips; see its header). To add clips or pieces, add them to its keep lists and rerun it rather than committing the full packs. Game code must keep working when `chars.ready` or `dun.ready` is false (primitive fallback). Monster clip choices are in `src/data/monsters.js`, dungeon layout tuning in `src/data/dungeon.js`.
- The owner builds from his phone, so changes are checked headless: run `npm run build && npm test` before every push. To look at the game, take a screenshot with `SCREENSHOT=/tmp/shot.png npm test`.
- What to build next, step by step: `docs/build-order.md`. Tick a step off there when it's done.
- Bluetooth is deliberately last. The current focus is making the ARPG fun with keyboard, mouse and touch.
- Pushing to `main` deploys to GitHub Pages.
- While the game is being built, the owner has authorised Claude to open a PR to `main` and merge it once `npm run build && npm test` pass, without asking each time. Work on the session branch, never push straight to `main`, and say in the reply what was merged. Ask first for anything risky or hard to undo (deleting content, big asset changes, upgrading three.js). Wiping old saves is fine (see above).
